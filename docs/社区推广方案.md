## 0. 结论先行

1. **不要再把 `dsh-desktop` 当"产品"推**。`dsh-desktop` 这个关键词已经被两个万星项目占领（31,119★ / 14,619★），你这个 0★ 的仓库在搜索、榜单、话题页里没有任何曝光位。它的正确身份是**"如何造一个 dsh 外壳"的参考实现 + Linux 唯一交付**。
2. **把 `dsh-desktop-hos` 当旗舰**，但卖点不是"又一个桌面壳"，而是 **"我们把 Electron 跑在了鸿蒙上"**——这是整个生态里没人做成、也几乎没人写过的技术事实。鸿蒙赛道已有 4 个玩家，但**全是 Node/ArkUI 路线，没有一个 Electron**，这是你唯一守得住的差异点。
3. **推广的杠杆不在"发帖"，而在"留下的东西"**：上游 dsh 的 patch、ohpm 上的 ArkTS 桥接组件、一篇别人写不出来的踩坑长文。250k★ 的上游仓库一次 merge，胜过一百条自荐贴。

## 5. 鸿蒙社区专项打法

### 5.1 先认清赛道的形状

- **不是无人区**：4 个同类项目已在（dshm 49★ 领先），但**全部不是 Electron 路线**。
- **你的护城河只有一条**：Electron 语义的 100% 复用 + 13 个 patch 的根因分析。所以鸿蒙侧的每一篇内容都必须围绕**"Electron 遇到鸿蒙"这个冲突**，而不是"又一个 AI 应用"。
- **分发存在结构性障碍**（必须提前想清楚，否则做多少内容都换不来安装量）：
  - debug 签名 × 他人设备 = 装不上（profile 设备绑定）；
  - release 签名 = 只能上架 AppGallery，`hdc install` 会被拒（`9568322`）；
  - 上架 = ACL 受限权限审核（≈3 工作日）+ AI 合规三件套（算法备案 / 大模型登记 / 安全评估）。
  - **结论**：鸿蒙侧的社区目标在 6 个月内应该是 **"技术影响力 + 开发者可自行构建"**，而不是"消费级下载量"。把 KPI 定在 star/下载量会误判自己。

### 5.2 受众分层：两条内容线，不要混着写

鸿蒙社区的实际读者是两拨人，混写会两头都不讨好：

| | 线 1｜技术硬核 | 线 2｜体验破圈 |

### 5.6 平台规则与坑（决定内容能不能被看见）

- **外链限制**：多数中文技术社区对正文外链降权。做法：开头不放仓库链接，把地址放在文末「代码与复现」段，评论区再置顶一次。
- **首发声明**：一稿多平台分发时，文首标「本文首发于 X」，显著降低被判搬运/洗稿的概率。
- **标题里要有一个具体名词**：`Electron`、`127.0.0.1`、`ALLOW_WRITABLE_CODE_MEMORY` 这类词是搜索入口；"鸿蒙 AI 工作台实践"没有长尾。
- **不要通篇卖产品**：鸿蒙社区对软文极敏感。产品提及压在文末一段，前面只讲问题与解法。
- **合规用词**：上架前的公开演示避免"官方""内置 DeepSeek"等表述（见 §8）。
- **版本时效**：每篇文首标"验证于 HarmonyOS 6.1.0.135 / API 24"，否则一年后会被当过期资料。

### 5.7 与鸿蒙生态的"正确关系"

1. **回馈运行时**：`harmonypc-electron`（AtomGit，jianguoxu）是你的地基。把 app 层的通用适配（prune/overlay 机制、`libc++_shared` 注入、`MediaAdapter`/`JsBindingMethod` 覆盖）整理成 PR 或 issue 回给他——他的一次转发，等于鸿蒙 Electron 圈子的入场券。
2. **降低别人的复现成本**：写一份《Electron 应用移植到鸿蒙的检查清单》（10 条），做成模板仓库。这是最容易被 star、fork、引用的形态。
3. **不要攻击 dshm**：它覆盖手机形态且不需要 JIT 权限，是另一条合理路线。正确话术是分工——"要手机形态选 dshm，要 100% 桌面语义选 Electron 路线"。**互相引用比互相比较更能带来流量。**
