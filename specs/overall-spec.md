# overall-spec.md — 整体规格

> 工程：`deepseek-harness-workspace`
> 范围：父工程 + 四个交付版本（桌面版、Electron on HarmonyOS 版、HarmonyOS 版、Android 版）。
> 本文档只描述 **WHAT / WHY**，不包含框架名、文件路径等实现细节；实现见各子工程 `specs/` 与 `overall-plan.md`。
> Last Updated: 2026-11-01

---

## 1. 系统目的

本系统把开源 Agent Harness（dsh）的官方 Web UI 交付为**四个平台上的本地原生应用**，让用户在 Windows / Linux / macOS / HarmonyOS / Android 上：

- 使用与上游一致的会话、工具、插件、设置与主题；
- 所有数据与模型调用发生在本地/用户可控环境，不依赖中转服务；
- 获得各平台的原生能力（窗口、托盘/通知、文件选择、剪贴板、后台保活等）；
- 通过插件市场安装/卸载 dsh 插件，通过 Git 工具管理代码仓库。

系统不是 dsh 的分叉，也不是重新实现的聊天客户端；它是 dsh Host 的**平台装配层**。

## 2. 目标用户与场景

| 用户 | 场景 | 关键诉求 |
|------|------|----------|
| 桌面开发者 | 在 Windows/Linux/macOS 上长期使用 dsh | 安装简单、窗口/托盘/通知原生、可打包分发 |
| HarmonyOS 用户 | 在 2in1/平板上使用 dsh | 不依赖 Android 兼容层、安装不需要高风险权限、界面与桌面一致 |
| Android 用户 | 在手机/平板上使用 dsh | APK 侧载、文件选择、通知、后台保活 |
| 插件作者/极客 | 扩展 dsh 能力 | 插件市场、Git 工具、技能、可审计的能力边界 |
| 维护者 | 跟随 dsh 上游升级 | 版本可复现、patch 可审计、四版能力语义一致 |

## 3. 核心能力（用户故事）

- 作为用户，我可以启动应用并看到 dsh 官方 Web UI，登录/配置后开始会话。
- 作为用户，我可以在会话中使用文件读写、命令执行、搜索、Git、图像理解等工具（能力因平台而异，差异必须可见）。
- 作为用户，我可以安装/卸载/启用/禁用插件，并在重启后保留状态。
- 作为用户，我可以选择工作区目录，并在授权范围内读写文件。
- 作为用户，我可以收到 agent 完成/审批的原生通知，并在后台保持任务运行（平台支持时）。
- 作为用户，我可以看到统一的产品品牌（名称、图标、窗口标题、Web 品牌位）。
- 作为维护者，我可以在一个工作区中复现四个版本的构建，并按版本更新流程升级上游。

## 4. 功能需求（按领域）

### 4.1 应用身份与品牌（BRAND）

- FR-BRAND-001：每个交付版本 MUST 有稳定的产品名称、应用图标与窗口/启动标题。
- FR-BRAND-002：应用级品牌（安装图标、应用名、通知图标）与 Web UI 品牌位 MUST 使用同一产品身份；允许平台后缀差异，但 MUST 在规格中登记。
- FR-BRAND-003：品牌物料 MUST 有单一来源，并按固定路径分发；更新物料 MUST 不改变代码引用。
- FR-BRAND-004：应用级身份（安装包、应用名、窗口/启动标题、通知）MUST NOT 呈现上游默认身份（如 “Electron”、上游鱼形 logo）；Web UI 内部品牌位在未实现 seam 的版本 MAY 显示上游品牌，但 MUST 在规格中登记。

### 4.2 运行时与启动（RUN）

- FR-RUN-001：应用 MUST 在自身进程内启动 Agent Host，并对外提供同源 Web 界面与 API。
- FR-RUN-002：启动 MUST 使用随机空闲端口，避免端口冲突。
- FR-RUN-003：启动失败 MUST 呈现可见错误/兜底页，MUST NOT 静默白屏或无限重试。
- FR-RUN-004：应用 MUST 单实例运行；重复启动 MUST 聚焦已有实例。
- FR-RUN-005：退出 MUST 优雅释放 Host 资源；平台不允许重启 Host 时 MUST 明确终态并提供重启应用的入口。
- FR-RUN-006：启动 MUST 校验运行时/载荷完整性（版本、哈希、关键文件），失败时给出可诊断信息。

### 4.3 界面与外壳（UI）

- FR-UI-001：界面 MUST 复用官方 dsh Web UI，MUST NOT 重写聊天界面。
- FR-UI-002：外壳 MUST 提供平台原生窗口行为（最小化/最大化/关闭/全屏/窗口状态恢复，平台支持时）。
- FR-UI-003：外壳 MUST 限制导航范围；外部链接 MUST 交给系统浏览器。
- FR-UI-004：加载/错误/空状态 MUST 有明确视觉反馈，MUST NOT 出现无反馈的空白。
- FR-UI-005：桌面版 SHOULD 提供系统托盘；HarmonyOS/Android 版按平台能力提供状态栏/通知入口。

### 4.4 宿主能力（CAP）

- FR-CAP-001：文件读写、列目录、搜索、命令执行、Git、通知、剪贴板、图像等能力 MUST 通过 Host 工具/能力桥暴露，MUST NOT 由渲染层直接调用平台 API。
- FR-CAP-002：未实现的能力 MUST 返回明确的 `not-implemented` / `unregistered` 及提示，MUST NOT 伪造成功。
- FR-CAP-003：能力调用 MUST 结构化进出（JSON），异常 MUST 转换为错误结果，不得导致应用崩溃。
- FR-CAP-004：文件类能力 MUST 遵守工作区/授权根围栏；超出范围 MUST 拒绝并说明。
- FR-CAP-005：命令执行 MUST 明确其隔离级别；无沙箱/围栏为 best-effort 时 MUST 在文档与 UI 中登记。
- FR-CAP-006：平台能力差异（PTY、原生搜索、图像转换、后台任务等）MUST 在能力矩阵中逐项登记。

### 4.5 数据与工作区（DATA）

- FR-DATA-001：会话、设置、凭据 MUST 存放在应用私有目录；凭据 MUST NOT 进入日志或仓库。
- FR-DATA-002：工作区 MUST 由用户显式选择/授权；应用 MUST NOT 默认扫描全盘。
- FR-DATA-003：载荷/运行时更新 MUST 幂等；重复启动 MUST 复用已校验产物。
- FR-DATA-004：数据目录布局 MUST 有单一事实源（常量/文档一致），MUST NOT 在代码中散落相对路径。

### 4.6 插件与生态（ECO）

- FR-ECO-001：应用 MUST 内置插件市场，并支持插件的安装、卸载、启用、禁用与状态持久化。
- FR-ECO-002：插件安装通道 MUST 在无系统 node/pnpm 的平台可用（进程内包管理器或等效方案）。
- FR-ECO-003：插件/技能 MUST 区分“通用可共享”与“壳专用”两层，并按约定目录放置。
- FR-ECO-004：Git 能力 MUST 在无系统 git 二进制的平台可用（纯 JS 实现或等效方案）。

### 4.7 诊断与可观测（DIAG）

- FR-DIAG-001：应用 MUST 提供可获取的诊断信息（版本、运行时、Host 状态、错误、日志尾）。
- FR-DIAG-002：诊断端点/入口 MUST 有访问控制（debug-only 或本地 loopback），MUST NOT 泄露 token/凭据。
- FR-DIAG-003：崩溃/未捕获异常 MUST 被记录，MUST NOT 静默消失。
- FR-DIAG-004：验收结论 MUST 附证据（命令输出、截图、JSON、日志片段）。

### 4.8 合规与发布（REL）

- FR-REL-001：发布产物 MUST 有明确版本号与单调递增的构建号（平台要求时）。
- FR-REL-002：签名材料 MUST NOT 入库；CI/本地签名 MUST 通过 Secrets/本地文件注入。
- FR-REL-003：权限声明 MUST 最小化、按需触发；商店版本 MUST 遵守商店权限策略。
- FR-REL-004：二进制/载荷 MUST NOT 入库；MUST 由脚本投放并校验哈希。
- FR-REL-005：发布说明 MUST 包含上游版本、运行时版本、已知限制。

### 4.9 版本更新（VER）

- FR-VER-001：上游 dsh 升级 MUST 以版本模块记录（`011-version-<VERSION>`），包含 patch 适配、构建、验证与文档同步。
- FR-VER-002：升级 MUST 保持“版本三元组”一致：应用版本、dsh tag、运行时版本。
- FR-VER-003：升级后 MUST 重跑四版能力矩阵/回归，差异 MUST 登记。

## 5. 平台差异（行为级）

| 能力 | 桌面版 | Electron on HarmonyOS | HarmonyOS 版 | Android 版 |
|------|--------|-----------------------|--------------|------------|
| 界面 | 官方 Web UI | 官方 Web UI | 官方 Web UI | 官方 Web UI |
| 窗口/托盘 | 窗口 + 托盘 | 窗口 + 状态栏 | 窗口 | 窗口 + 通知 |
| 命令执行 | 完整 | 非 PTY shell | 非 PTY shell（受限） | 非 PTY shell |
| PTY/终端 | 支持 | 不支持 | 不支持 | 不支持（暂缓） |
| 原生搜索 | 支持 | 支持 | 受限（纯 JS） | 纯 JS 替身 |
| Git | 系统/内置 | 纯 JS 21 工具 | 纯 JS 21 工具 | 纯 JS 21 工具 |
| 插件市场 | 内置 | 内置 | 内置 | 内置 |
| 后台保活 | 平台能力 | 受限 | 受限 | 前台服务保活 |
| 安装权限 | 无 | JIT ACL（Electron 路线） | 默认零 ACL | All-files（full）/ SAF（store） |
| 品牌 | 桌面品牌 | 桌面品牌 | 应用名带 Ark 后缀 + Web 品牌 | 统一品牌 |

> 完整 42 项能力矩阵见 `docs/能力对照清单.md`；各子工程 `overall-spec.md` 与模块 `spec.md` 为工程内事实源。

## 6. 非功能需求

### 6.1 性能

- 冷启动到可交互 SHOULD 在平台可接受范围内；启动失败 MUST 在有限时间内可见。
- 大载荷解包 MUST 流式/幂等，MUST NOT 一次性读入内存。
- 包体 SHOULD 控制（ark 默认无 Chromium；Android 单 ABI）。

### 6.2 可靠性

- Host 崩溃/异常 MUST 有日志与兜底；不允许静默退出。
- 载荷/运行时校验失败 MUST 阻止进入半可用状态。
- 单实例/端口随机 MUST 避免多实例争用。

### 6.3 安全与隐私

- 凭据、token、签名材料 MUST NOT 入库/进日志。
- 明文网络仅 loopback；外部导航交系统浏览器。
- 权限最小化；文件访问受工作区/授权根约束。
- 上游 patch MUST 可审计、幂等。

### 6.4 可维护性

- 四版共享编号与能力语义；差异显式登记。
- 上游升级路径明确（tag、patch、profile、seam、垫片）。
- 文档 as-built、可追溯、无占位符。

### 6.5 国际化与可访问性

- 品牌字符串与 UI 文案 SHOULD 支持中英文（上游已提供 i18n）。
- 平台原生控件 SHOULD 遵循系统可访问性语义。

## 7. 系统边界

### 7.1 在范围内

- dsh Host 的启动、装配、平台能力适配。
- 四个交付壳的窗口/生命周期/构建/发布。
- 插件市场与 Git 工具在受限平台的可用方案。
- 品牌化、版本更新、诊断与验收。

### 7.2 不在范围内

- 修改 dsh 的核心 Agent 逻辑或重写 Web UI。
- 自建云端模型服务/中转服务。
- 操作系统级沙箱/内核开发。
- 商店运营、市场推广（见 `docs/` 推广方案，不属产品规格）。
- 未在能力矩阵登记的实验性能力。

## 8. 验收场景（跨工程）

### 场景：首次启动

- Given 用户安装任一版本
- When 首次启动
- Then 应用校验运行时/载荷、启动 Host、加载官方 Web UI；失败时显示可诊断错误页

### 场景：完成一次会话

- Given 已配置模型凭据
- When 用户创建会话并发送消息
- Then agent 正常回复；工具调用按平台能力执行或返回明确不支持

### 场景：安装插件

- Given 打开插件市场
- When 用户安装一个插件
- Then 插件安装成功并出现在设置中；重启后仍生效（平台支持时）

### 场景：能力降级

- Given 平台不支持 PTY/原生搜索
- When 用户触发相关能力
- Then 返回明确提示/降级结果，不伪造成功

### 场景：版本升级

- Given 上游发布新 tag
- When 按 `011-version-*` 流程升级
- Then 四版构建通过、能力矩阵回归、文档同步

## 9. 假设与约束

- 上游 dsh 为 developer preview，接口/结构可能变化；每版锁定一个 tag。
- HarmonyOS/Android 的平台限制（无 ELF 执行、无 PTY、无 JIT 等）为硬约束，需以能力矩阵登记。
- 四个版本的构建环境不同（Node/Electron/DevEco/Gradle），不要求统一工具链。
- 本文档不替代各子工程的模块级验收；冲突时以源码与子工程 as-built spec 为准，并回写本文档。
